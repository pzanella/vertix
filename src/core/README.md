# `@vertix/core` (currently `src/core/`)

The reframe engine, on its own. No React, no UI framework, no dependency
on how the video got onto the page. This folder is written so it could
become its own npm package later — everything in here is plain
TypeScript plus the compiled WASM face detector.

## What it does

Give it a `<video>` element and a `<canvas>` element. It:

1. Detects faces in the video a few times a second (Rust/WASM, via a
   small pretrained model).
2. Decides how many of those faces are real on-camera speakers (filters
   out small/distant/partially-cropped ones).
3. Picks a layout for that many speakers — one wide chest-up crop, a
   stacked split for two, a grid for three or more, or no crop at all if
   there are zero.
4. Draws that layout to the canvas, every video frame, with a stable,
   gently-smoothed camera and a soft cross-dissolve whenever the layout
   itself changes.

It does **not** load a video file, does not call `.play()`/`.pause()`, and
does not set `.currentTime`. It only *reads* the video element and reacts
to its native events (`play`, `seeking`, `loadedmetadata`). Whatever
already controls playback — your own `<video>` tag, or a media framework —
keeps full control.

## Usage

```ts
import { VertixEngine } from "./core"; // or "@vertix/core" once published

const engine = new VertixEngine();
engine.attach(videoElement, canvasElement);
engine.setMode("9:16"); // or "16:9" for the untouched original

const unsubscribe = engine.onMetricsUpdate((metrics) => {
  console.log(`fps: ${metrics.fps.toFixed(1)}`);
});

// Later, if you're swapping to a different video/canvas pair:
engine.attach(otherVideo, otherCanvas);

// When you're completely done with it:
engine.destroy();
```

## API

| Method | What it does |
| --- | --- |
| `attach(video, canvas)` | Starts reframing this video onto this canvas. Safe to call again with a different pair — the old one is detached first. |
| `detach()` | Stops rendering and removes listeners from the current video. The WASM engine stays warm for a future `attach`. |
| `destroy()` | Full teardown, including the WASM instance. Construct a new `VertixEngine` if you need one again. |
| `setMode(mode)` | `"16:9"` (untouched original) or `"9:16"` (reframed). |
| `getMode()` | Current mode. |
| `onMetricsUpdate(listener)` | Subscribe to live telemetry (FPS, detection confidence, motion, ...) — a few times a second. Fires once immediately with the current values, then on every update. Returns an unsubscribe function. |
| `onStateChange(listener)` | Subscribe to everything else that changes (mode, video dimensions, speaker count, whether a transition is in progress, whether WASM has finished loading). Same immediate-fire-then-updates contract. Returns an unsubscribe function. |
| `getMetrics()` / `getState()` | Read the current snapshot without subscribing. |
| `setLookaheadEnabled(enabled)` | Lookahead on (default) or off at runtime: see [Lookahead](#lookahead). |
| `getLookaheadStatus()` | Whether lookahead runs, its length, why it is unavailable, buffer size and memory. |
| `getDisplayedMediaTime()` | Media time of the frame on screen (behind `video.currentTime` by the lookahead while playing). |
| `setBenchmarkProbe(probe \| null)` | Benchmark mode only: report per-frame and per-detection timings to a `BenchmarkProbe` (e.g. a `BenchmarkRecorder`). `null` (the default) turns it off. See `docs/benchmark.md`. |

## Files in here

- **`VertixEngine.ts`** — the class above. Owns the frame loop
  (`requestVideoFrameCallback`), the lookahead display loop
  (`requestAnimationFrame`), the face-detection cadence, and all the
  timing/smoothing constants (how long to wait before trusting a speaker
  count change, how big the camera's dead zone is, how long a layout
  cross-dissolve takes, ...). If something about *when* or *how fast* the
  camera reacts needs tuning, it's a constant near the top of this file.
- **`layoutEngine.ts`** — pure functions, no engine state. Given a list of
  detected faces and some dimensions, works out the crop rectangles. This
  is where the "how wide is the crop" (`SINGLE_SPEAKER_ZOOM_FACTOR` /
  `MULTI_SPEAKER_ZOOM_FACTOR`) and "where does the face sit in the crop"
  (`FACE_VERTICAL_ANCHOR`) constants live.
- **`wasm/`** — generated by `npm run build:wasm` from `wasm/src/` at the
  repo root (the actual Rust source): `simd/` and `scalar/` builds plus
  `buildInfo.json`. Gitignored, not hand-edited.
- **`wasmBuild.ts`** — SIMD support probe and the import of the matching
  build. `VertixEngine` loads the selected build in the worker and in the
  main-thread fallback; `switchWasmBuild()` exists for the benchmark suite.
- **`bench/`** — benchmark mode: `BenchmarkRecorder` (preallocated sample
  buffers), `stats.ts` (pure percentile/summary functions), environment
  probe, JSON/CSV report builders, and `runBenchmarkClip` /
  `runUnrecordedWarmup`. Nothing here runs unless a probe is attached.
- **`index.ts`** — the public export surface.

## Design notes

Playback ownership stays with the host on purpose. This is what makes
attaching to a Shaka Player, hls.js, or Video.js-managed video element
work without any special integration code; see
[`../../docs/player-integration.md`](../../docs/player-integration.md) for
a worked example.

Detection runs off the main thread, in a single Worker shared by every
`VertixEngine` instance the page ever constructs (`getSharedDetectionWorker`
near the top of `VertixEngine.ts`) — not just the WASM inference call, but
the pixel readback that feeds it too (`faceDetectionWorker.ts` owns its
own `OffscreenCanvas` for that). Falls back to running both synchronously
on the main thread if the worker can't be built, errors, or doesn't report
ready within `WORKER_READY_TIMEOUT_MS`. See the README's own "Known
Limitations" for how this got here — an early attempt did add enough
round-trip latency to read as disconnected panning, but that was a
one-worker-per-instance mistake, not a reason to avoid a worker at all.

A crash discovered well after the worker reported ready — not just an
initial-load failure — is recovered from the same way: `fail()` (inside
`getSharedDetectionWorker`) always tears the worker down and flips
`sharedWorkerReady` off, and `dispatchDetection`'s fallback branch calls
`ensureWasm()` lazily on its own next tick, even for an instance that
never needed its own WASM engine before.

The layout only changes when the speaker *count* changes, debounced over a
short time in seconds (dropping to zero speakers reacts faster than any
other change, since staying cropped over a shot with no one in it looks
worse than briefly widening out), or on a hard cut in the source, which
the WASM detector reports (`wasm/src/scene_cut.rs`: a colour or layout
score of at least 0.12 that is also 3x its recent median, and at least
1.0 s of media time after the previous cut) and which commits the new
count at once and snaps the crop. Within a stable layout, individual
crops move only past a dead zone, then glide; the full layout decision
never reruns, except when the active speaker switches to someone far
away, which cross-dissolves instead of panning. This two-layer design, a stable layout plus independently-smoothed
positions within it, came out of several rounds of tuning against real
footage. If camera movement still feels off, look at the constants in
`layoutEngine.ts` (`PANE_SMOOTHING_TAU_SEC`), `VertixEngine.ts`
(`DEADZONE_FRACTION`) and `speakerTracking.ts` (`PERSON_COUNT_STABLE_SEC`),
not the layout math itself.

## Lookahead

With lookahead on (the default), every decoded frame is copied into a ring
of `OffscreenCanvas` slots (`lookahead/frameRingBuffer.ts`) and drawn by a
`requestAnimationFrame` loop at its own display time plus the lookahead
length. The audio goes through the same delay (`audioActivity.ts`: a
`DelayNode` after the analyser). Detection results become decisions stamped
with their frame's media time (`lookahead/decisionTimeline.ts`) and are
applied when that frame is drawn, so a snap after a cut, a speaker-switch
dissolve or a layout change lands on the frame it belongs to.

- **Length**: 2 × detection p95 + cut-trigger p95 + one frame, kept within
  120–600 ms (`lookahead/lookaheadSizing.ts`). Per-device and per-build
  defaults until this device has measured its own (stored in
  `localStorage`). It only changes at a seek, a source change or the
  switch, never mid-playback.
- **Frame copies**: the largest size (source size first) at which the
  frames needed fit 96 MiB. Copies are drawn from the video synchronously,
  so no decoder frame is held.
- **Cut trigger**: a 64×48 thumbnail of every frame goes to
  `cutTriggerWorker.ts`; a likely cut starts a detection on that frame at
  once instead of at the next 5-frame tick. The WASM detector still
  decides. A cut found on a regular tick is moved back to the frame with
  the biggest frame-to-frame jump.
- **Unavailable**: without a Web Audio graph (the element's own audio
  could not be delayed), or for a cross-origin source without CORS (a
  tainted canvas, or exact silence for 3 s from a cross-origin element
  that is playing audio and has never produced sound),
  lookahead is forced off and reported in `getLookaheadStatus()`.
- **Playback events**: pause drains the buffer (video and audio stop
  together, on the frame at `currentTime`); play and seek refill it (the
  last frame holds, audio is silent, for the lookahead length); a frame
  shown while paused waits for its own detection, and after a seek while
  paused that detection commits the speaker count at once, like a cut; rate changes and
  rendition switches need nothing special.
